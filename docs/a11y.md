# Accessibility (A11y) Guide
This guide covers how to build accessible UI in BetterYTM. It's meant for both refactoring existing code and writing new components. Keep it in mind whenever you create interactive elements, dialogs, icons, or form controls. Plugins are also encouraged to adhere to these conventions.

<br>

## 1. Naming elements: `ariaLabel` vs `title`
- **`ariaLabel`** is the accessible name read by screen readers. Required on any interactive element that has no visible text (icon buttons, icon links).
- **`title`** is a mouse-hover tooltip. It's a nice-to-have for sighted users, not a substitute for `ariaLabel`.
- **Don't** set `ariaLabel` on elements that already have clear visible text (e.g. a button labeled "Save") - it's redundant and can break voice-control software, which matches against the accessible name rather than the visible label.
- **Don't** rely on `title` alone for icon-only controls - it's not consistently exposed to screen readers and has no touch/keyboard equivalent.

<br>

## 2. Custom interactive elements
Never build a clickable `<div>`/`<span>`/`<a>` with only a `click` listener. Screen reader and keyboard users can't operate it.  
Use the project's existing helper, [`onInteraction`](../src/utils/input.ts), which wires up both `click` and `keydown` (Enter/Space) with one call:
```ts
import { onInteraction } from "@utils/input.ts";

el.role = "button";
el.tabIndex = 0;
el.ariaLabel = el.title = t("do_thing");
onInteraction(el, () => doThing());
```

**Checklist for every custom clickable element:**
- [ ] `role="button"` (or a more specific role, e.g. `"switch"`, `"link"`)
- [ ] `tabIndex = 0` so it's keyboard-focusable
- [ ] `ariaLabel`/`title` if there's no visible text
- [ ] Click **and** keydown (Enter/Space) handled - use `onInteraction`, don't hand-roll a raw `addEventListener("click", …)`

If a native `<button>` works visually (can be restyled), prefer it - it gets focusability, keyboard activation, and the right default role for free, with no helper needed.

<br>

## 3. Images & icons
- **Decorative icon** (purely visual, meaning is already conveyed by a label elsewhere): give it `alt=""`, or `aria-hidden="true"` if it's an inline SVG. This stops screen readers from announcing it.
- **Meaningful image** (conveys information, e.g. a logo or an image that *is* the content): give it a real, descriptive `alt`.
- If an icon is wrapped in an element that already has `ariaLabel`/`title` (e.g. `src/features/featAdornments.ts`), mark the inner `<svg>`/`<img>` as `aria-hidden="true"` so it isn't announced twice.

<br>

## 4. Toggles, switches & form controls
`src/components/toggleInput.ts` is the reference implementation - follow its pattern for any custom toggle:
- Wrapper: `role="switch"`, `tabIndex = 0`, `ariaChecked` kept in sync with state on every change.
- A real `<label htmlFor="...">` pointing at the (visually hidden but present) `<input type="checkbox">`, not just an `ariaLabel` on a div.
- Keydown handler for Space/Enter that mirrors the click behavior.

For plain form inputs, prefer `<label for="id">` over `aria-label`. Only fall back to `aria-label`/`aria-labelledby`/`aria-describedby` when a visible label isn't feasible (e.g. a compact icon-only search box, or an input element you don't control.

<br>

## 5. Dialogs & menus
Current dialog/menu code (`src/components/BytmDialog.ts`, `src/menu/menu.ts`) sets `role="dialog"` and `aria-modal="true"` and closes on Escape, which is the preferred way.

<br>

## 6. Keyboard support checklist
For any new interactive component, make sure:
- Enter/Space activates buttons and toggles.
- Escape closes dialogs/menus/popovers.
- Tab order follows visual/logical order, and nothing focusable is skipped or hidden behind `tabIndex="-1"` by mistake.
- Custom "checkbox" elements (like `checkboxEl.tabIndex = -1` in `toggleInput.ts`) that are only there to hold state can stay non-focusable, but only if their wrapper is focusable and fully operable - don't hide the *only* focusable element.

<br>

## 7. Focus visibility
Never disable the focus ring with `outline: none` without providing a replacement `:focus-visible` style - keyboard users need to see where they are.

<br>

## 8. Quick pre-merge checklist
When you add or touch interactive UI, ask:
1. Can this be operated with keyboard only (Tab + Enter/Space + Escape where relevant)?
2. Does every icon-only control have `ariaLabel`?
3. Are decorative icons hidden from AT (`alt=""` / `aria-hidden="true"`)?
4. Does a custom control expose the right `role` and state (`aria-checked`, `aria-expanded`, `aria-pressed`, etc.) and keep it in sync?
5. If it's a dialog: does it trap focus and restore it on close?
6. Is the focus ring still visible when tabbing to it?
7. (Optional) Test UIs with a screenreader software like [NVDA.](https://www.nvaccess.org/download/)

When in doubt, prefer reusing `onInteraction` (`src/utils/input.ts`) and the `toggleInput.ts` pattern over inventing a new one.
